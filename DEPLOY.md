# Deploy your own Tallya

This repository is the public demo: the data you see is fictional, generated by
`assets/seed.js`. What follows sets up **your own instance**, with your figures,
reachable from any device and readable by nobody else.

Everything fits in Cloudflare's free tier. Budget half an hour the first time.

> **Read step 4 before you enter a single amount.** A fresh deployment is closed
> by default — `_worker.js` refuses to serve anything, static files included,
> until you configure a password or Cloudflare Access. That is deliberate, and it
> is why the door comes before the furniture.

---

## What gets set up

| Piece | Role | Cost |
|---|---|---|
| **Cloudflare Pages** | hosts the site | free |
| **`_worker.js`** | quote gateway and access control | free, 100k req/day |
| **KV** | stores your state, shared across devices | free, 1000 writes/day |
| **Cloudflare Access** | the front door: one-time email code | free up to 50 users |

You get a `your-project.pages.dev` address. A domain of your own works too and
is entirely optional.

---

## 1. Get the files onto Cloudflare

Two routes. Drag-and-drop is faster to try; Git redeploys on every push.

**Drag and drop.** In the Cloudflare dashboard, **Compute → Workers & Pages →
Create → Pages → Upload assets**. Name the project, drag the whole cloned folder
in, **Deploy site**. `_worker.js` is picked up automatically.

**From Git.** Fork this repository, then **Workers & Pages → Create → Pages →
Connect to Git**, pick your fork, and leave every build setting empty:

| Setting | Value |
|---|---|
| Framework preset | None |
| Build command | *(empty)* |
| Build output directory | `/` |

There is no build step, which is the point: the files in the repository are the
files the browser runs.

> **If you replace `assets/seed.js` with your own figures, make your fork
> private.** The seed in *this* repository is fictional and safe to publish;
> yours would not be. Your day-to-day data never goes through Git — it lives in
> the browser and in KV — so most people never touch the seed at all.

---

## 2. Create the KV store

1. **Storage & databases → KV → Create a namespace**. Call it whatever you like.
2. Back on your Pages project: **Settings → Bindings → Add binding → KV
   namespace**.
   - Variable name: **`WEALTH`** — exactly that, the code looks it up by name.
   - KV namespace: the one you just created.
3. Add the binding for **Production** *and* **Preview**.
4. **Deployments → Retry deployment**, so the binding takes effect.

Without this the app still works, but each device keeps its own state. The
binding is what makes them one.

---

## 3. Close the door

Either option is enough on its own. You can also use both.

### Password

**Settings → Variables and Secrets → Add variable**, type **Secret** (not Text —
a secret is never displayed again), name `DASHBOARD_PASSWORD`, value a long
unique password. Save and deploy.

A signed cookie then holds a 30-day session. Changing the password invalidates
every open session immediately.

### Cloudflare Access (recommended)

Filtering happens *before* the request reaches the code, so an application bug
cannot leak anything.

1. **Zero Trust → Access → Applications → Add an application → Self-hosted**.
2. Session duration `1 month`, domain = your exact `.pages.dev` address.
3. **Add policy**: action `Allow`, include → **Emails** → your address.
4. Login method: **One-time PIN** is enough.

**Then set two variables, and this part is not optional.** On the Access
application page, copy the **Application Audience (AUD) Tag**, then in your Pages
project under *Settings → Variables and Secrets*:

| Name | Value |
|---|---|
| `ACCESS_TEAM_DOMAIN` | `your-team.cloudflareaccess.com` |
| `ACCESS_AUD` | the AUD tag you just copied |

The worker validates the Access token's signature against your team's public
keys, so it has to know which team and which application. Without these two
values no Access identity is recognised and the password path takes over — you
cannot lock yourself out with this setting.

This matters more than it looks. Before that validation existed, the mere
presence of a `Cf-Access-*` header counted as an identity, and that same header
chose the storage key.

> **Always check in a private window.** You must land on a sign-in screen, never
> on the dashboard. Test an API path too — `…pages.dev/api/health` must answer
> `403`.

## 4. First run

Open the address and sign in. On the **Data** tab, the *online sync* card should
show your email and an active state. On the **Markets** tab, refresh quotes to
confirm the gateway works. Then open the same address on your phone and use *Add
to home screen*: it installs as an app, works offline, and shares the same state.

---

## How conflicts are handled

There is no merge, and saying so is the honest part.

Every save carries the version it read. On load, if the online state is newer
than the local one, the app **asks** which to keep; it never decides alone. On
save, if the server holds a newer version it answers `409`, and you choose:
take the online one, or overwrite with yours. Saves are debounced and only write
when something actually changed, which keeps a normal day far below the free
tier's 1000 writes.

Advice all the same: do not enter figures on two devices at the same moment.

---

## Local mode

`python serve.py` keeps working, offline included. Note that local and online are
**two separate stores** — different browsers, different origins. Pick one as your
reference, or move data across with the JSON export and import.

---

## What this implies

Your financial data will be hosted **at Cloudflare**, not on your machine. Under
the GDPR you remain its controller:

- Protection rests entirely on step 3. Without it everything is public, which is
  why that step comes before you enter anything.
- If you abandon the project, delete the KV namespace, the Pages project and the
  repository. Data should not outlive its purpose.
- Cloudflare can technically read what is stored in KV — it is not
  end-to-end encrypted. If that bothers you, stay local.
